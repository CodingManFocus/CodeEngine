# Code Engine 0.1.0 검증 보고서

## 현재 변경: 비동기 이벤트 종료 대기 — 2026-09-25

앞선 감사의 F3 재현 경로를 수정했다. 관리 대상 이벤트가 실행 중일 때 unload/reload가 클래스로더와 빌드 파일을 먼저 닫던 문제다. 공개 CodeModule/ModuleContext API 시그니처와 원본 Paper 객체 전달은 유지했다.

### 종료 정책

1. 새 이벤트 진입을 원자적으로 차단하고 명령·리스너·타이머 등록을 해제한다.
2. 이미 진입한 관리 대상 이벤트가 반환할 때까지 기다린다. 메인 스레드에서 get/join/await로 대기하지 않는다. 대기 모듈이 있을 때만 공유 스케줄러 작업 하나가 매 틱 완료를 확인한다.
3. 완료되면 메인 스레드에서 disable을 실행하고 클래스로더와 빌드 파일을 정리한다. reload는 이 단계가 성공한 뒤에만 새 소스를 읽고 컴파일·load한다.
4. 기본 10초(`unloadTimeoutSeconds`, 1~300초) 초과 시 작업은 실패한다. 모듈은 Stopping 상태로 남고 같은 모듈의 작업을 차단한다. 클래스로더·파일은 유지하며 콜백이 나중에 반환하면 자동 정리한다. 시간 초과한 reload는 자동 재시작하지 않는다.
5. 일부 등록 후 활성화 실패한 후보도 같은 대기와 정리 경로를 사용한다.
6. 엔진/서버 종료 중 실행 중인 이벤트가 남으면 경고를 남기고 해당 모듈의 disable을 건너뛴다. 콜백 반환 후 Paper API와 사용자 훅을 호출하지 않고 클래스 로더·파일만 정리한다. 콜백이 끝나지 않으면 JVM 종료까지 자원을 유지한다.

### 수정 전후 검증

- 동일한 새 회귀 검사를 수정 전 JAR에 실행해 `NoClassDefFoundError: ...m_asyncunload.Entry$1`와 조기 unload 완료를 재현했다.
- 수정 후 JAR로 실제 Paper 독립 JVM **2개에서 각각 391개 검사 성공**, 각 서버 정상 종료. 해당 오류는 재현되지 않았다.
- JUnit **51/51개 성공**. 신규 6개 검사에는 동기·비동기 진입 추적, 동기 콜백 중 재진입 종료, 예외/Error 뒤 카운터 해제, 닫힌 실행기 재진입 거부, 4개 작업 스레드로 100회 반복하는 진입/종료 경쟁 검사가 있다.
- 실서버 검사에서 일반 unload, reload, 예외를 던지는 콜백, 시간 초과, 부분 활성화 실패를 확인했다. 콜백 종료 전 산출물 유지, 이전에 로드하지 않은 익명 클래스 로딩, 종료 후 파일 삭제, disable의 메인 스레드 실행과 순서를 검증했다.
- 비동기 콜백이 메인 스레드 작업의 결과를 기다리는 경우에도 종료 대기가 메인 스레드를 막지 않아 완료됐다. 이미 캐시된 RegisteredListener의 실행도 종료 차단 이후 모듈 코드에 재진입하지 못했다.
- 시간 초과 검사는 설정을 1초로 줄여 실행했다. 제한 시간 이후 재로드 차단, 늦게 종료한 콜백의 자동 정리, 실패한 reload의 자동 재시작 없음, 정리 후 명시적 load 성공을 확인했다.
- 엔진 종료 경로는 실제 Paper 위의 별도 ModuleManager 인스턴스에서 검사했다. 실행 중 콜백 및 reload 대기 중 close를 호출해 disable 생략과 콜백 반환 후 산출물 정리를 확인했다. disable이 manager.close를 재진입 호출하는 경우에도 훅이 한 번만 실행되고 실행 중 클래스로더가 닫히지 않았다.
- JDK 21 `javac --release 21`로 전체 제품·검증 코드 컴파일 후 JAR를 조립했다. 이번 실행에서 Gradle clean build는 수행하지 않았다.
- 환경: Paper 1.21.11 build 132 / Corretto 21.0.12.1+9-LTS / 접속자 0명. 실제 Paper AsyncPlayerChatEvent 디스패처와 Player proxy를 사용했으며, 실제 플레이어의 채팅 네트워크 경로는 검사하지 않았다.

현재 JAR SHA-256: `61fb111b320ee1c4c16d53e2838d65295f3483089a592ed5363ac2f45a47bb8d`.

### 검증 범위와 비용

앞선 감사의 F1~F5는 각 재현 조건에 대한 수정과 회귀 검증을 완료했다. 임의의 Java 코드 전체나 장기 운영의 무오류를 증명한 것은 아니다. 관리 대상은 DSL 이벤트와 ctx.listen이며, 직접 생성한 스레드와 외부 콜백의 자동 종료는 제공하지 않는다.

비동기 이벤트에는 원자적 카운터 연산, 동기 이벤트에는 상태 확인과 호출 수 기록 비용이 추가된다. Paper API 자체의 호출은 그대로 유지한다. 이번 통합 실행은 기존 명령 벤치마크도 수행했지만, 이벤트 추적 비용을 별도로 분해 측정한 결과는 아니다. 메인 스레드에서 이벤트 완료를 기다리지 않는다는 뜻이며, 비용 0이나 사용자 enable/disable 코드가 메인 스레드를 지연시키지 않는다는 보장은 아니다.

자료: `verification/results/async-before/`, `verification/results/async-after/`의 원본 로그·checks·JUnit XML·environment.json. 재현 코드는 `AsyncLifecycleVerification.java`, `EventActivityTest.java`와 `verification/run-integration.py`에 있다. 아래는 이전 구현 기준의 변경 이력이다.

## 이전 변경: 공유 Listener 소유권 수정 — 2026-09-25

앞선 감사의 F5를 수정했다. `ModuleScope`는 모듈마다 전용 Listener 하나를 생성해 Paper 등록과 해제에 사용한다.
`ctx.listen` 호출자가 넘긴 Listener가 다른 모듈 또는 외부 등록과 공유되어도 그 등록은 해제하지 않는다.
실제 EventExecutor에는 원본 Listener와 원본 Event를 전달하며, 이벤트 우선순위와 ignoreCancelled는 Paper가 처리한다.
등록용 객체와 실행 연결 콜백은 등록 시 생성한다. 이벤트마다 객체를 복사하거나 새 게임 객체 래퍼를 만들지 않는다.
Paper의 등록 목록에는 모듈 전용 Listener가 보이므로 외부 코드에서 caller Listener의 동일성으로 등록을 검색하던 동작과는 다르다.
공개 API 메서드 시그니처는 변경하지 않았다.

### 당시 보류한 문제

**이 변경 당시에는 F3(진행 중 비동기 이벤트의 unload 이후 클래스 로딩 오류)를 수정하지 않았다. 이후 수정과 검증 결과는 이 문서 최상단을 따른다.**
콜백 완료 추적과 메인 스레드를 막지 않는 종료 대기는 구현 방향이 될 수 있다. 그러나 끝나지 않는
핸들러의 처리, 대기 중 load/reload 요청, 서버 종료 시 메인 스레드에서 실행해야 하는 disable 처리,
부분 활성화 실패 시 이미 시작된 콜백 정리까지 일관된 정책이 필요하다.
메인 스레드를 단순히 기다리게 하면 해당 스레드의 작업을 기다리는 콜백과 교착할 수 있고,
제한 시간 뒤 클래스로더를 강제로 닫으면 기존 오류를 다시 만들 수 있다.
사용자의 “방법이 명확치 않으면 하지 말라”는 조건에 따라 이번에는 그 정책과 코드를 임의로 변경하지 않았다.
이것이 기술적으로 해결 불가능하다는 뜻은 아니다.

이 변경 당시 앞선 5종 감사 문제 중 F1/F2/F4/F5는 해당 재현 조건의 회귀 검사를 통과했고,
F3는 남아 있었다. 임의로 직접 등록한 작업·외부 스레드의 자동 정리도 여전히 지원 범위 밖이다.
이번 변경의 이벤트 실행 비용을 별도 성능 벤치마크로 분해 측정하지 않았으며, 비용 0이나 완전한 성능 동등성을 주장하지 않는다.

아래 내용은 이전 변경과 최초 검증의 이력이다. 각 수치는 해당 당시 구현 기준이다.

## unload 후 load 방식으로 reload 변경 — 2026-09-25

현재 reload는 **기존 모듈의 unload 완료 → 소스 읽기·컴파일 → 새 모듈 load** 순서다.
이전 모듈 복구 경로는 제거했다. 컴파일하는 동안 모듈은 미실행 상태다.

- 기존 등록 해제, disable, 클래스 로더 종료 및 빌드 정리를 완료한 뒤 컴파일을 시작한다.
- unload/disable이 실패하면 남은 정리를 시도하고 실패로 완료한다. 새 코드의 컴파일·enable은 시작하지 않는다.
- 컴파일·생성자·enable·이벤트 등록이 실패해도 이전 모듈을 재활성화하지 않는다.
- 실패 후 loaded 목록과 명령 등록 상태가 미실행 상태를 반영한다.
- build는 실행 중인 모듈을 유지하는 별도의 사전 검사다. 미실행 모듈에 reload를 요청하면 load와 동일하게 동작한다.
- reload 전체에 같은 모듈의 작업 중복 방지가 적용된다. 생명주기 변경은 메인 스레드, 컴파일은 전용 작업 스레드에서 수행한다.

### 이번 변경 검증

- JDK 21 `javac --release 21`로 전체 제품 및 검증 소스 컴파일 성공.
- 기존 JUnit **45개 성공**. XML 결과: `verification/results/reload/junit/`.
- 변경된 실제 Paper 통합 검사 **295개 성공**, 정상 종료. 기존 20회 연속 리로드 검사를 포함한다.
- 이전 disable의 저장 후 새 enable이 읽어 카운터 1이 유지됨을 확인했다. 다음 unload 뒤 저장값도 1이다.
- 파일 잠금이 이전 disable에서 해제된 후 새 enable에서 정상 획득됐다.
- disable의 AssertionError가 unload/reload의 실패 결과로 전달되었다.
- disable 실패가 새 소스의 컴파일 오류보다 먼저 보고되었고, 새 enable의 표식 파일이 생성되지 않았다.
- build 실패는 실행 모듈을 유지하지만 reload의 컴파일·생성자·enable·등록 오류와 소스 파일 누락은 모듈을 미실행 상태로 남겼다.
- 실패한 reload 뒤 기존 타이머가 재실행되지 않았고, 명령·namespaced 명령·리스너·작업·빌드 디렉토리의 잔존이 없었다.
- 실서버 원본 로그·검사 결과·생성 소스는 `verification/results/reload/fork-1/`에 있다.
- 빌드 시 이번 환경에 준비된 Paper 배포본의 의존성과 JDK를 사용해 직접 javac/JAR 조립을 수행했다. 이번 실행에서 Gradle clean build를 수행했다고 주장하지 않는다.

검사한 배포 JAR SHA-256: `8b7c9444ca6f33a6066ba7f2ba1cdf2ed4783935823343bbf582da73a0c7acb8`.

### 남아 있는 수명 관리 범위

앞선 감사의 F1(저장 순서/독점 자원), F2(종료 오류 성공 응답), F4(취소 타이머 복구 중 재실행)는 이번 경로 변경과 오류 전파로 회귀 검사를 통과했다.
이 리로드 개편 시점에는 F3(진행 중인 비동기 이벤트 종료 대기)와 F5(공유 Listener 소유권)가 남아 있었다. F3/F5의 후속 수정 상태는 이 문서 상단을 따른다.
직접 등록한 Paper 작업·외부 스레드·파일/월드 변경의 자동 롤백도 제공하지 않는다.
실제 접속자와 장기 운영, 모든 임의 사용자 코드의 완전한 종료를 증명한 검사는 아니다.

아래는 변경 전 구현의 검증/벤치마크 이력이다. 특히 기존 모듈 유지·복구에 관한 검사는
변경 전 동작이며 현재 정책은 위 내용을 따른다. 과거 3개 JVM의 수치를 이번 JAR의 새 벤치마크 결과로 해석하지 않는다.

## 실행 시간

단위는 **µs/명령 작업 1회**입니다. Paper CommandMap dispatch, 인수 파싱, 응답 문자열·메시지 전달 경로가 포함됩니다. 실제 채팅·네트워크 I/O는 포함하지 않습니다.

| 동일 작업 | 일반 Java 플러그인 | Code Engine | CE / Java |
|---|---:|---:|---:|
| long 정수 계산 1,024회 | 2.1123 | 2.1023 | 0.995× |
| 실제 블록 조회·Material 비교 256회 | 5.4216 | 5.2709 | 0.972× |

각 JVM의 배치 평균 120개에 대한 중앙값을 구한 뒤, 세 JVM 중앙값의 중앙값을 대표값으로 사용했습니다. **이번 작업의 실행 시간은 Java 기준에 가까웠습니다. 1~3% 차이를 성능 우위로 해석하지 않습니다.** 다른 모듈·서버 부하·JIT 상태에서도 이 비율을 보장하지 않습니다.

| JVM | Java 계산 | CE 계산 | Java 블록 | CE 블록 |
|---|---:|---:|---:|---:|
| 1 | 2.1142 | 2.1023 | 5.0174 | 5.1030 |
| 2 | 2.0656 | 2.0713 | 5.4216 | 5.2709 |

## 메모리 할당

| 동일 작업 | Java B/작업 | CE B/작업 |
|---|---:|---:|
| 계산 1,024회 | 3086.25 | 3087.50 |
| 블록 조회 256회 | 3078.75 | 4796.16 |

메인 스레드 ThreadMXBean의 할당 카운터입니다. 유지되는 힙 크기나 전체 서버 메모리가 아닙니다. **블록 조회 작업은 CE 쪽이 약 1.56배 많이 할당했습니다.** 코드의 객체 변환 래퍼는 제거했지만, 이번 조건에서 할당량까지 Java와 같아지지는 않았습니다. 이 차이가 어느 객체·최적화 결정에서 발생했는지는 분해 측정하지 않았습니다. 따라서 무할당이나 완전한 성능 동등성을 주장하지 않습니다.

이 차이를 줄이기 위해 각 모듈이 native `Command` 하위 클래스를 직접 생성하는 대안도 구현·검증했습니다. 대안에서는 대표 블록 조회 시간이 Java 대비 약 **1.133×**였고 할당량은 거의 줄지 않았습니다. 최종 구현은 더 빠르게 측정된 단일 `NativeCommand`와 native Paper `CommandExecutor` 등록 경로를 선택했습니다. 대안의 raw CSV·생성 소스·바이트코드는 `verification/results/direct-command-experiment/`에 별도로 보존했습니다. 이 실험용 생성 JAR를 서버 플러그인으로 설치하면 안 됩니다.

## 측정 조건과 한계

- Paper 1.21.11 build 132, commit `c5eb079`, SHA-256 `5ffef465eeeb5f2a3c23a24419d97c51afd7dbb4923ff42df9a3f58bba1ccfba`.
- Amazon Corretto 21.0.12.1+9-LTS, Linux x86_64, `-Xms512M -Xmx2G`, 기본 GC. 공유 실행 환경으로 CPU 스케줄링 변동은 통제하지 못했습니다.
- 새 독립 서버 3개. seed 123456789, flat 월드, 플레이어 0명, view/simulation distance 2, spark 비활성. 블록 작업은 미리 채운 같은 chunk에서 stone/dirt 패턴을 읽습니다.
- 각 JVM에서 120틱 워밍업 + 120틱 측정. 틱마다 네 작업의 순서를 고정 seed로 섞고 작업당 128개 명령을 실행합니다. 원시 CSV는 JVM당 480행입니다.
- 명령 문자열은 사전에 생성하며 64개 seed를 반복합니다. 기능 동등성은 64개 입력 전부에서 별도로 확인합니다. 측정 중 응답은 같은 capturing sender에 전달됩니다.
- Java 기준 코드는 정상 Paper 플러그인 명령입니다. CE는 실제 `.ce` 컴파일·JAR·ClassLoader 로딩 경로를 사용합니다. Java 기준 플러그인에는 테스트 제어 때문에 엔진 의존성이 있지만, 기준 계산·블록 조회 본문은 엔진 API를 호출하지 않습니다.
- 두 구현은 같은 JVM·같은 서버에서 비교됩니다. 서로 별도 JVM에서 단독 실행한 비교가 아닙니다. 독립 JVM 반복은 이런 동일 조건의 쌍 비교를 3회 수행한 것입니다.
- 이벤트 검증의 Player는 실제 클라이언트가 아닌 접근 시 실패하는 proxy이고, World·Block·BlockBreakEvent·이벤트 디스패처는 실제 Paper입니다. 실제 플레이어 채굴 전체 경로를 검증한 것은 아닙니다.
- 이벤트 처리 시간, 동시 접속 부하, 네트워크, 전체 TPS·MSPT, 장시간 GC/힙 보유, 종료 중 무한 사용자 코드 등은 측정하지 않았습니다.
- 테스트 환경에서 Mojang 공개키 및 Paper 업데이트 확인 DNS 실패 로그가 있습니다. offline-mode 격리 서버에서 모듈 동작·측정은 완료했으며 로그에 원문을 남겼습니다.
