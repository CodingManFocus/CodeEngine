# 외부 플러그인 Java API

모듈은 서버에 설치된 플러그인의 공개 Java API를 직접 호출할 수 있습니다.
호출은 일반 Java 바이트코드로 컴파일되며, API 호출마다 플러그인을 검색하거나
리플렉션·객체 래퍼를 거치지 않습니다. 의존 플러그인 JAR는 모듈 JAR에 포함하지 않습니다.

```java
module placeholders;
requires plugin "PlaceholderAPI";

use me.clip.placeholderapi.PlaceholderAPI;

command ceparse permission "codeengine.examples" {
    if (!(sender instanceof Player player)) {
        sender.sendMessage("플레이어만 사용할 수 있습니다.");
        return true;
    }
    String input = String.join(" ", args);
    player.sendMessage(Component.text(PlaceholderAPI.setPlaceholders(player, input)));
    return true;
}
```

`/ceparse <사용할 플레이스홀더>`의 치환 결과는 설치된 PlaceholderAPI 확장에 따라 달라집니다.
이 예제 파일은 `examples/placeholders.ce`에도 있습니다. 자동으로 설치하지 않습니다.

## 선언과 지원 범위

- `requires plugin "이름";`에는 플러그인의 파일명이 아닌 정확한 등록 이름을 씁니다.
  영문자·숫자·`_`·`.`·`-`를 허용하며 중복 선언은 거부합니다.
- `build`, `load`, `reload` 모두 선언한 플러그인이 활성화되어 있어야 합니다.
  CodeEngine 자체는 이미 사용 가능하므로 의존성으로 선언할 수 없습니다.
- 최초 지원 대상은 **Bukkit `plugin.yml` 형식의 JavaPlugin**입니다.
  `paper-plugin.yml` 형식은 지원하지 않습니다. Paper 내부 클래스 로더나
  의존성 그래프를 수정해 접근 권한을 우회하지 않습니다.
- 직접 사용할 API와 그 시그니처의 타입은 서버 기본 클래스패스 또는
  명시적으로 선언한 플러그인 JAR에서 찾을 수 있어야 합니다.
  플러그인이 별도 로더로 내려받는 API·라이브러리, 중첩 JAR API는 지원하지 않습니다.
- 서로 다른 선언된 플러그인의 동일한 클래스 이름, 서버/엔진 클래스와의 중복은
  순서에 따라 임의 선택하지 않고 컴파일 전에 거부합니다.
- 다중 Java 버전용 provider JAR(`Multi-Release`) 및 manifest의 추가 `Class-Path`는
  컴파일/실행에서 타입 출처가 달라지는 것을 방지하기 위해 거부합니다.
- CodeEngine은 추가 플러그인·라이브러리를 자동 다운로드하지 않습니다.
  Paper가 실제 로드한 로컬 JAR 위치를 사용합니다. 실행 중 JAR를 덮어쓰지 말고
  서버 재시작으로 업데이트하십시오.

이 선언은 CodeEngine 모듈의 의존성을 나타냅니다. Paper의 플러그인 시작·종료
의존성 그래프에 모듈을 추가하지 않습니다. 따라서 일반 JavaPlugin의 `depend`와
같은 종료 순서를 보장하지 않습니다. **정상 서버 종료 중에도 의존 플러그인이
CodeEngine보다 먼저 종료되면 모듈의 `disable`과 외부 정리 작업을 건너뜁니다.**
외부 API를 호출하는 정리 작업이 반드시 필요한 경우, 의존 플러그인이 활성화된
동안 모듈을 먼저 `unload`하고 성공을 확인한 뒤 서버를 종료하십시오.
플러그인이 활성화된 것과 데이터나
외부 서비스가 준비된 것은 다릅니다. 각 API의 준비 상태, 스레드 규칙 및 버전 변경은
모듈 작성자가 처리해야 합니다.

## 컴파일과 클래스 연결

1. 작업 스레드에서 모듈 소스 하나를 읽고 파싱합니다.
2. 서버 스레드에서 의존 플러그인의 인스턴스·로더·JAR 위치를 고정합니다.
3. 작업 스레드에서 클래스 충돌을 검사하고 고정된 클래스패스로 컴파일합니다.
   annotation processor와 의존 JAR의 소스 자동 컴파일은 비활성화합니다.
4. 서버 스레드에서 인스턴스와 로더가 그대로인지 재검사한 뒤 모듈을 초기화합니다.
   생성자·prepare·enable·등록 이후에도 엔진과 의존성의 상태를 확인합니다.
5. 모듈 로더는 모듈 클래스만 정의합니다. 외부 타입은 캡처한 플러그인 로더에
   위임하며, 실제 클래스의 정의 로더와 JAR가 컴파일 때의 출처와 같은지 확인합니다.

외부 플러그인의 JAR를 모듈 로더의 URL 목록에 넣지 않습니다. 모듈을 해제해도
외부 플러그인의 로더를 닫지 않습니다. 연결 검사는 클래스 해석 시 수행하며
이미 연결된 API 메서드를 호출할 때 실행하는 중계 코드는 없습니다.

## 외부 등록 정리

`ctx.onClose(AutoCloseable)`은 `enable` 또는 등록 준비 단계에서 서버 스레드로 호출합니다.
외부 API에 등록한 직후 해당 등록을 해제하는 작업을 넘기십시오.

```java
// 외부 API의 register가 성공한 직후, 해당 등록만 해제하도록 등록합니다.
ctx.onClose(() -> expansion.unregister());
```

정상 종료 순서는 관리 대상 이벤트·명령·반복 작업의 신규 진입 차단 → 진행 중인
관리 대상 호출 종료 → `disable` → 등록한 정리 작업의 역순 실행 → 모듈 로더·빌드 파일 정리입니다.
정리 하나가 실패해도 나머지를 시도하고 예외를 함께 보고합니다.
실패한 `enable`에서 이미 등록한 정리 작업에도 같은 절차를 적용합니다.

이 기능은 임의의 외부 콜백을 가로채거나 추적하지 않습니다. 비동기 콜백을 직접
등록했다면 해제 함수가 앞으로의 실행을 차단하는지, 진행 중인 콜백의 종료를
어떻게 보장할지도 해당 API의 계약에 따라 처리해야 합니다.

`ctx.plugin()`은 모든 모듈에 대해 **CodeEngine의 Plugin 인스턴스**를 반환합니다.
모듈은 독립적인 JavaPlugin이 아닙니다. 외부 API가 Plugin 하나당 등록 하나만
허용하거나 Plugin 전체를 일괄 해제한다면 모듈 간 독립성을 보장할 수 없습니다.
`unregisterAll(ctx.plugin())`, `cancelTasks(ctx.plugin())` 같은 엔진 전체 정리는
사용하지 말고 해당 모듈의 개별 등록 핸들을 해제하십시오.

## 의존 플러그인이 종료되는 경우

운영 중 의존 플러그인의 hot disable/reload는 지원하지 않습니다. 종료 이벤트를
받으면 해당 인스턴스를 즉시 무효화하고 의존 모듈의 관리 대상 신규 실행을 차단합니다.
컴파일 중인 모듈도 활성화 전에 거부합니다. 같은 플러그인 인스턴스를 다시 enable해도
무효화는 해제하지 않으므로 서버를 재시작해야 합니다.

이미 종료에 들어간 플러그인을 호출하지 않기 위해 사용자 `disable` 및 등록된
정리 작업을 건너뛰고 명시적으로 실패를 보고합니다. 각 정리 작업 직전에도 의존성을
다시 검사합니다. 진행 중인 외부 호출을 강제로 중단하거나, 외부 플러그인이 보관한
참조를 자동 제거할 수는 없습니다. 이런 상태에서는 재시작하십시오.

서버/엔진 종료 때 관리 대상 콜백이 아직 실행 중이면 메인 스레드에서 기다리지 않습니다.
사용자 종료 코드를 건너뛰고 콜백 반환 후 산출물만 정리합니다.
이 보호는 모듈 자신의 파일을 너무 일찍 닫지 않기 위한 것입니다. CodeEngine이나
의존 플러그인 자체를 비활성화한 뒤 해당 플러그인의 새로운 타입을 로드하거나
API를 계속 사용하는 것은 보장하지 않습니다. 해당 로더의 수명은 Paper가 관리합니다.
운영 업데이트에는 서버 재시작을 사용하고, 모듈 load/unload/reload는 개발용으로 사용하십시오.

## 검증

무료 PlaceholderAPI의 실제 공개 API를 사용한 순수 Java 플러그인과 모듈 비교는
`verification-external`에서 재현할 수 있습니다. 컴파일 시간, API 직접 호출,
명령 처리 전체의 비용을 구분합니다. ItemsAdder는 설치하거나 테스트하지 않았으며,
그 플러그인의 모든 API와 호환된다는 보증은 아닙니다.
